# UI auditor

A deterministic crawler that finds generic UI defects in the demo-mode app. No LLM, no feature knowledge: it clicks controls
as a real user would (mouse at the control's centre), replays each path from a clean browser, and compares states.

Run: `cd web && npm run audit` (builds the UI first; about 3.5 minutes on 8 cores with both themes, down from about 23 serially). Output in `web/audit-out/`:
`ui-findings.json`, `graph.json` (states and edges per crawl), `screens/` (one screenshot per state) and `views/<root>-<viewport>-<theme>.png` (the start state of each root in each viewport and theme: a gallery to look at).
It is a reporter, not a gate: the test passes whatever it finds.

## How it runs
One Playwright test per (root, viewport), spread over `AUDIT_WORKERS` workers (default: the CPU count, at most 10). Each worker starts its own demo server (own port and data folder) from a worker-scoped fixture; each crawl writes `audit-out/parts/<crawl>.json`, and the global teardown merges the parts, in crawl order, into `ui-findings.json` and `graph.json` with the same dedupe and scoring as a serial run. A crawl keeps one browser context and opens a new page (storage of the origin cleared) per reset. A page has settled when none of its requests is pending and the DOM has not mutated for 150 ms (3 s cap). `summary.timing` (and `perCrawl[].timing`) shows where the time went: reset, replay, act, settle (overlaps the others), snapshot, screenshot.

## What it crawls
Each top-level view (Canvas, Graph, Graph (populated), Concepts, Ask, and the Agent access dialog) is its own start state with its own budget
(depth 3, up to 40 states, 45 crawl actions, 20 return attempts and 8 toggle replays), at 1500x900 and again at 1280x720.
**Theme is a crawl dimension**: every root is crawled in light and dark mode (Playwright `colorScheme`; the app follows it by default). Light runs at both viewports; dark runs at 1500x900 only, because the 1280x720 crawl finds layout problems that do not depend on the theme and a dark copy of it would add about 40% to the run time (`AUDIT_DARK_ALL=1` adds it, `AUDIT_THEMES=light` or `dark` narrows). With the dark 1500x900 crawls a full run is about 3.5 minutes on 8 cores. Every finding's `where` entries carry the theme; `summary.byTheme` gives the score, style score and findings per rule for each theme. Style lint measures light only (the dark values are the same tokens, and pooling both would double the distinct colours).
**Graph (populated)** is the Graph tab with the demo fact table opened and two more hops added (12 tables, the way `e2e/helpers.ts` does it), so the Graph is judged with nodes and edges on it; its gallery pictures are `views/graph-populated-<viewport>-<theme>.png`, plus `graph-populated-selected-...` with one table selected and the details panel open.
Its budget is smaller (30 actions, 10 return attempts, 4 toggle replays) because each replay rebuilds a 12-table layout.
A group of pressed buttons where pressing one releases another (the Flow, Model and All lenses) is a choice among options: pressing the pressed one again is not a toggle, and the one A had pressed is tried first on the way back.
The top-level tabs are roots, so they are not clicked inside a crawl. Override the budget with `AUDIT_ACTIONS`, `AUDIT_STATES`,
`AUDIT_DEPTH`, `AUDIT_EXTRA`, `AUDIT_TOGGLES`. Findings are deduplicated across roots and viewports; `where` lists each place one appeared.

## Rules
| rule | severity | meaning |
| --- | --- | --- |
| irreversible-transition | high | action takes A to B and no way back to A within 2 actions was found; the finding says what B has that A lacks |
| toggle-not-undoable | high | a control whose label or pressed/expanded state changed (a toggle) is clicked again in B, at its centre, and does not lead back to A; reports what the click hit and how the result differs from A |
| occluded-control | high | another element covers the centre of the visible part of a control |
| only-obscure-exit | medium | B gets back to A only through Escape or a control not visible in A at the same screen position. Not obscure: a dialog's own buttons (B opened a dialog A lacked), the opener of a dialog that A had and B closed, a control labelled Close, Cancel, Done, Back, Undo or Restore, and the opposite of a control A shows (Hide X / Show X, Open / Close, Expand / Collapse, Maximize / Restore, Zoom In / Zoom Out). Before reporting, B's other actions are tried (opposite first), because the way-back search stops at the first exit it finds, often Escape. `confidence` is `low` when B still has untried actions |
| overlapping-controls | medium | two controls' boxes intersect (neither contains the other) |
| offscreen-control | medium | a control is partly outside the viewport |
| escape-does-nothing | low (confidence low) | B has a dialog, menu, listbox, popover or aria-haspopup control with aria-expanded=true that A lacked, and Escape changes nothing (plain pressed toggles and expanders are not expected to close on Escape) |
| region-separation | medium | adjacent or nested major regions that cannot be told apart. Regions are found generically: landmarks (header, nav, aside, main, [role=region], [role=dialog], banner, navigation, complementary), React Flow's canvas pane and nodes, and elements with `data-region` (add that attribute in the app only where no landmark fits). Two regions are adjacent when neither contains the other, their gap is at most 8px (a resize handle) and they share an edge of 24px or more; a region is also compared with the region it sits in (not when it fills 85% of it). Each pair passes if the backgrounds differ by at least CIEDE2000 2, or the facing edges have a border of 1px or more in a colour that differs from both backgrounds, or either has a box-shadow. A React Flow node is a bare wrapper, so the box inside it that fills it is measured. The finding names both regions and the two backgrounds and deltaE. `regions.ts` |
| surface-order | medium (low confidence for a missing declaration) | one elevation order in every view and theme. Regions declare a role in `data-surface`: `base` (app shell, sidebars, toolbars), `recessed` (canvas floors, the graph pane), `raised` (content panes, cards, windows, notes, graph nodes) or `overlay` (dialogs, popovers, menus). Per view and theme the measured background luminance (the opaque colour after blending ancestors; the biggest area wins when a role has several colours; selected elements are skipped) must satisfy: raised and overlay lighter than base; recessed not lighter than base in light, darker than base in dark; overlay at least as light as raised; raised lighter than recessed. Across views, each role must have one background per theme (within 2 per channel): the merge reports a role whose colour differs between roots. A region over 15% of the viewport with no `data-surface` on itself or an ancestor is a low-confidence finding. `surfaces.ts` |
| clipped-text | low | text is wider than its box with no ellipsis |
| contrast | high on a control, medium on other text | text below WCAG contrast (4.5:1; 3:1 for text of 24px+ or 18.66px+ bold) against its effective background: the ancestors' backgrounds alpha-blended until one is opaque, white if none is. An element with a background-image on its own or an ancestor is skipped (unknown). Disabled controls, inert and aria-hidden content are skipped, as WCAG exempts them. The finding names the selector, the colour pair and the ratio. `contrast.ts`; states hover, focus and active are not crawled, so check those by hand |
| small-target | info | under 24x24 px; does not count toward the score |

Style lint rules (below) are separate: they never count toward this score.

## Comparing states
States in the crawl graph are keyed by a strict signature (every control with its name and pressed/expanded state). Whenever a state is compared with A (is B back at A, is a toggle undone, is a transition irreversible) the comparison is **loose**: states are the same if they differ only in selection, meaning aria-selected, a `data-selection-ui` attribute on the control or an ancestor (the app marks UI that exists only while something is selected, such as Duplicate, Delete and Arrange), a `selected` / `is-selected` class, resize handles, and controls that are enabled in one state and disabled in the other (clicking inside a window selects it, which enables Duplicate and Delete and shows handles). A control that is part of the selection may appear or vanish without counting. Findings say what differed (`only before: ...`, `only after: ...`); an only-obscure-exit lists what a loose match overlooked. `graph.json` keeps each state's full control list (`controls`, with `[disabled]` and `[selection]` marks) so a difference can be checked by hand.

## Reset
Every action replays from a clean browser context and emptied server stores (`canvases`, `canvas_history`, `diagrams`, `diagram_history`, `relationships`, which holds concepts). A store missing from that list makes every later reset start somewhere else: Concepts at 1500x900 once logged about 100 reset failures because the concepts a click had saved were still there. `summary.perCrawl[].resetFailures` counts mismatches and `resetDiffs` shows what the start state had extra or lacked. `AUDIT_ROOTS=Concepts,Canvas` and `AUDIT_VIEWPORTS=1500` narrow a run.

## Measurement
- A control counts as visible only if part of its box shows inside every ancestor that clips (overflow other than visible, clip-path, contain:paint) and the viewport, and it is not inert, aria-hidden, visibility:hidden or opacity 0. Occlusion tests and clicks use the centre of the visible part.
- When modal dialogs are open (aria-modal, or a role=dialog inside a backdrop), only controls inside the topmost one are active; the rest are out of scope for actions and for occlusion/overlap checks.

## Score
Severity weights are 10 high, 4 medium, 1 low, 0 info. Each distinct root cause counts once: findings with an occluder (occluded and overlapping) are grouped by occluder and a group counts once, at its highest severity; every other finding counts once. Findings the rule labels `confidence: low` (an only-obscure-exit whose B still had untried actions; every escape-does-nothing, a heuristic) count a quarter of their weight, and all of them together at most 15, so a pile of uncertain findings cannot drive the score to 1. Info findings weigh 0. With T the weighted total, score = round(100 * exp(-T / 50)): 100 is clean, about 82 at T=10, 37 at T=50, 13 at T=100; the low-confidence ceiling alone costs at most 26 points (score 74 at T=15). `summary.weightedCauses` is T, `summary.lowConfidenceFindings` and `lowConfidenceWeight` show the low-confidence part. Expected findings (below) are excluded. `summary.weightedCauses` is T.

## Expected behaviour (`audit/expected.json`)
A list of `{rule, control, root?, viewport?, reason}`. `control` is the control's name (the text between the quotes in `control`) or a `/regex/` tested against the name and the whole label; `root` and `viewport` narrow it. `irreversible-transition` also matches the first click of the repro, since one one-way action shows up under each state it leads to. `reason` is required; a malformed entry or one without a reason fails the run before it starts.
Matching findings stay in `ui-findings.json` with `"expected": true` and `expectedReason`, are counted in `summary.expectedByRule` and not in `findingsByRule` or the score. Entries that match nothing are listed in `summary.staleExpected`: delete them.
Adding an entry is the maintainer's decision, not a fixing agent's. An agent that thinks a finding is by design says so in its report and leaves the file alone.
`summary.perCrawl[].unverified` lists the edges whose way back could not be fully checked (return-attempt budget used up), with the reason.

## Using ui-findings.json
1. Read `summary.rootCauses`: occluded and overlapping findings grouped by the element on top (class list, testid, nearest labelled ancestor), biggest first. Fix the top cause first; one CSS change usually clears many findings. Each has `examples`, a `repro` and a `screenshot`.
2. Then `findings` (sorted by severity, then by how many roots/viewports saw it). `repro` is the click path from the root's start state; `screenshot` is relative to `web/audit-out/`.
3. Fix in app code, rerun, and compare `findingsByRule`. Treat a finding as a crawler artefact if `repro` does not reproduce by hand.

## Style lint (consistency, not defects)
Amateur-looking UIs are mostly inconsistent ones, so this measures inconsistency and names the design tokens that would remove it. `style.ts`; the crawler only calls `StyleAcc.visit` at the first visit to each state (about 5-10% of the run time, `summary.timing.styleMs`). Deterministic, no LLM.

Collected per visible element, except those inside a zoomed canvas node (an ancestor with a transform that scales, which would measure the zoom rather than the design) (in a box inside the viewport, not display:none, visibility:hidden or opacity 0; clipping by scroll containers is not checked): font-size, font-weight and line-height and colour of elements with their own text; background colour; border colour; border radius; each non-zero padding side; flex/grid gap; the measured gap between adjacent siblings (whole px, 1-64, skipped where the parent declares a gap or spreads its children); button and input heights; boxes.

`ui-findings.json` gets a top-level `style` section: `summary` (score, distinct font sizes / colours / radii / spacings, per-state averages), `tokens` (per property: every distinct value with `uses` (element occurrences, summed over every first visit of a state, so shell elements count once per state), `states` and example selectors), pooled `colours` and `spacings`, `offScale` offenders and `perState` (distinct font sizes, colours, spacings and radii, and visible disabled controls as a clutter signal). Style findings are also in `findings` with `category: "style"`.

| rule | severity | meaning |
| --- | --- | --- |
| style-near-duplicate | low | two values that should be one: font sizes or radii within 1px, spacings (padding, gap, sibling gap, over 2px) within 1px, colours within CIEDE2000 < 3 (and alpha within 0.05). Names both with uses and examples and suggests merging into the more common. Top 40 by combined use |
| style-off-scale | low | declared padding or gap not on the 4px grid (0, 1 and 2px allowed). One finding per value, the 10 most used; `offScale` lists 25 |
| style-row-inconsistent | low | sibling buttons (or inputs/selects) on one row of the same container with different heights (1px or more), font sizes (0.5px or more) or radii. One per container |
| style-over-budget | low (1 per value over) | a kind of value has more distinct values than its budget: font sizes 5, radii 4, colours (text, background and border, pooled) 14, spacings (padding, gap, sibling gap, pooled) 10, control heights (buttons and inputs, rounded to 1px) 4. One finding per kind lists the least used values to fold first; **each value over budget adds 1 to the style total**, so it is not capped by the 40-per-rule limit. `style.summary.budgets` has distinct, budget and over for each |
| style-near-miss-align | low | siblings, or same-looking grandchildren of different children (cousins), whose left, right or centre-x (or top or centre-y) edges differ by 0.5-3px while no edge on that axis matches. One per container |

Style findings are deduplicated like the others and can be silenced in `expected.json` (the maintainer's call). The **style score** is separate: T is the sum of style finding weights (low 1, info 0) and `score = round(100 * exp(-T / 50))`, in `style.summary.score` and `summary.styleScore`. The functional `summary.score`, `findingsByRule` and `rootCauses` ignore style findings. Fix order: merge near-duplicates and off-scale values into tokens first (one token change clears many findings), then rows, then alignment.
