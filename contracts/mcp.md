# MCP server contract

A Model Context Protocol server inside the Flask app, so a coding agent (Claude Code, for example) can explore the catalog and work on canvases and saved graphs next to the person using the browser UI. Implemented in `mcp_server/`. It adds `/mcp` and the two `/api/agent-access` routes to `app.py` and changes nothing else about the API, except for the canvas revision routes in `contracts/api.md` section 3.

**Scope.** Read access, local edits, and read-only SQL. **No tool writes to the Databricks workspace, and no tool connects or chooses a profile or warehouse.** The agent uses whatever the person connected in the UI. A tool that needs a connection returns an error result that says "Not connected: connect a profile in the app first."

## Transport

MCP streamable HTTP at `POST /mcp` on the app's own port (`127.0.0.1` only), answered with `application/json`. There is no SSE stream. The JSON-RPC methods are handled directly in Flask.

| Request | Answer |
| --- | --- |
| `POST /mcp` with `initialize` | `200`, the result below, and a `Mcp-Session-Id` header |
| `POST /mcp` with a notification, or a response from the client | `202`, empty body |
| `POST /mcp` with a request | `200`, one JSON-RPC response |
| `POST /mcp` with a JSON array | `200`, an array of the responses (`202` when none) |
| `POST /mcp` with `server/discover` | `200`, error `-32601`. This is the handshake-free probe of protocol 2026-07-28; clients fall back to `initialize` |
| `GET /mcp` | `405` (`Allow: POST, DELETE`). The server never streams |
| `DELETE /mcp` with a session | `204` (`404` for an unknown session) |

**Methods:** `initialize`, `notifications/initialized` (and any other notification, ignored), `ping`, `tools/list`, `tools/call`. Anything else is error `-32601`.

**Protocol version.** `initialize` echoes the client's `protocolVersion` when it is one of `2025-11-25`, `2025-06-18`, `2025-03-26`, `2024-11-05`, and answers `2025-11-25` otherwise. A later request may carry `MCP-Protocol-Version`; an unsupported value is `400`. The initialize result is `{"protocolVersion", "capabilities": {"tools": {"listChanged": false}}, "serverInfo": {"name": "databricks-explore", "title", "version"}, "instructions"}`. Protocol 2026-07-28 itself (no handshake, no sessions) is not implemented.

**Sessions.** Every request except `initialize` needs `Mcp-Session-Id` (`400` when missing, `404` when unknown). A session id is a random part plus its HMAC under the token, so the server keeps no table and a session survives a restart of the app. A new token ends every session.

**Errors.**

- JSON-RPC errors (`{"jsonrpc": "2.0", "id", "error": {"code", "message"}}`): `-32700` invalid JSON (HTTP `400`), `-32600` not a JSON-RPC 2.0 request, an empty batch, a missing session or an unsupported protocol version (HTTP `400`, or `404` for an unknown session), `-32601` unknown method, `-32602` bad params or an unknown tool name.
- A tool that fails is **not** a JSON-RPC error. It is a normal result with `"isError": true` and the message as text, so the model can read it and correct the call. That includes arguments that fail the input schema (`Invalid arguments: ...`).

## Authentication and local-only checks

- **Token.** A random 32-byte URL-safe token is created at startup if `<data dir>/mcp_token` does not exist, and stored there with mode `0600` where the OS has file modes (a looser mode is tightened on next use; on Windows the file sits in the per-user folder). Every request to `/mcp` needs `Authorization: Bearer <token>` (compared in constant time), or it gets `401` with `WWW-Authenticate: Bearer`.
- **DNS rebinding.** A request whose `Host` is not `127.0.0.1`, `localhost` or `[::1]`, or whose `Origin` header is present and not one of those (`null` included), gets `403` before the token is looked at. A request with no `Origin` (a command line client) is fine.
- **Logging.** The token is never logged. Each tool call adds one line to `data/logs/calls.jsonl` with the tool name, milliseconds and success, and nothing else: no arguments, SQL or results.

### `GET /api/agent-access`

For the "Agent access" panel in the top bar. Same Host and Origin checks as `/mcp` (`403` otherwise), no token needed (the page is the owner).

```json
{"url": "http://127.0.0.1:8765/mcp", "token": "...",
 "command": "claude mcp add --transport http databricks-explore http://127.0.0.1:8765/mcp --header \"Authorization: Bearer ...\"",
 "tools": 47}
```

### `POST /api/agent-access/token`

Replaces the token and returns the same body. Agents using the old token get `401` until they are given the new command.

## Tool results

A result is `{"content": [...], "isError": false}`. Content is one text block, except `render_canvas`, which returns an `image` block (`mimeType: "image/png"`, base64) and a text block. Output is compact text by default. Tools that have a `format` argument return everything as JSON text with `"format": "json"`. Tool names, descriptions and input schemas are exactly what `tools/list` returns, with `annotations.readOnlyHint` set for the tools that change nothing. Every input schema is an object with `additionalProperties: false`.

## Tools: relationships and mining

Every edge kind belongs to a **family**: `flow` (`lineage`, `view_dep`: data moves from source to target), `reference` (`fk`, `join_mined`, `manual`: a key identifies a row elsewhere) or `meaning` (`sketch`, `concept_link`, `ontology`). `get_graph` and `lineage` report it next to the kind. `get_graph` also gives each reference edge's crow's-foot `cardinality` (`contracts/api.md`, `POST /api/relationships/cardinality`): the end at each table that is known, with its basis, and in text `[orders o<, customers ||]`. Each flow edge whose SQL the app has (a view's definition, or the statement last read for a table in the Graph) also carries its `transform` (`contracts/api.md`, `POST /api/edge-transforms`), and in text a bracket such as `[aggregates by order_date (SUM), joined inner on date_key]`; `[pass-through]` when the query changes nothing. It comes from the cache only, so an edge whose SQL was never read has none. Only flow edges set a graph's left-to-right order.

## Tool: run_sql

`run_sql(statement, max_rows?, timeout_s?, max_cell_chars?)` runs **one** read-only statement on the SQL warehouse the app selected.

- **Gate.** The statement is parsed with sqlglot (Databricks dialect). Exactly one statement is accepted, and it must be a `SELECT` or `WITH ... SELECT` (also `UNION` and a parenthesized query), `DESCRIBE`/`DESC`, `SHOW` or `EXPLAIN`. Everything else is rejected, with `Rejected: <reason>` as an error result and no call to the warehouse: other statement kinds (`INSERT`, `DROP`, `MERGE`, `COPY`, `OPTIMIZE`, `SET`, `USE`, `CALL`, ...), more than one statement, an empty or unparseable statement, `SELECT ... INTO`, any DML or DDL node anywhere in the tree (so none hides in a CTE or subquery), and the functions `reflect`, `java_method`, `try_reflect` and `http_request`.
- **Caps.** `max_rows` is 1 to 1000 (default 100). `timeout_s` is 1 to 300 (default 60). A statement still running at the timeout is cancelled (`statement.cancel`) and the result is an error. The statement runs through the app's usual `query_async` and `query_status`, so it is logged like any query.
- **Output.** Text: a `columns: name TYPE, ...` line (the warehouse's type text), a TSV header line, the rows, and a closing line such as `(5 row(s) shown; the query has more than 5 rows (cap 5); 412 ms)`. A cell longer than `max_cell_chars` (50 to 4000, default 200) is cut with `...`, tabs and newlines in a cell become spaces, `NULL` is the word `NULL`, and the rows stop at about 24,000 characters (the closing line then says so).
- **Metric views** are queried with `SELECT MEASURE(`name`) ... GROUP BY ...`, not `SELECT *` (the tool description says so).
- **Errors** (`isError`): rejected by the gate, not connected, no warehouse selected, timed out, or the warehouse's own error.

A canvas is the saved file of `contracts/api.md` section 3 (format version 2 for anything an agent writes; a version 1 file is rewritten as version 2 on the first agent edit). Canvas tools need no connection and no warehouse. **They always read and write the saved file**, never the page's unsaved state.

### Charts and results

A query window can keep the result of its last run, so whoever opens the canvas sees evidence without pressing Run on every window (`result` and `view` in `contracts/api.md` section 3). An agent fills it with `run_window` and `run_all_windows`, and draws a chart with `chart`.

- **`run_window(name, id, max_rows?, timeout_s?)`.** Expands the window's `{{title}}` references exactly as the page does (`sqltools.expand_refs` over the canvas's query windows), then runs the expanded SQL through the **same gate as `run_sql`**: `sqlguard.check_read_only` on the expanded text, so a DML or DDL statement in a referenced window is rejected too, and a rejection (`Rejected: ...`) happens before any warehouse call and writes nothing. The run, its polling, the timeout and its cancellation are `run_sql`'s (`submit_read_only` and `await_statement` in `tools_data.py`). On success the snapshot (`columns`, at most 500 `rows`, `row_count`, `truncated`, `ran_at`, `sql_hash` of the expanded SQL) is written into the window as an **agent write**: the canvas revision goes up, `by` is `agent`, and the file it replaced is kept first, so `undo_canvas` removes the result. `max_rows` defaults to 500, the most a window keeps, and `truncated` is true when the run was cut or fewer rows were kept than it returned. Errors: a bad id, a node that is not a query window, an unknown or cyclic `{{title}}`, the gate, not connected, no warehouse, a timeout, the warehouse's error. A locked window can still be run.
- **`run_all_windows(name, max_rows?, timeout_s?)`.** Runs every query window with SQL in dependency order: windows are grouped in levels, a level holding the windows whose references are all in earlier levels (canvas order inside a level), a whole level is submitted before any of it is awaited (so independent windows run on the warehouse together), and a window starts only after the windows it references have finished, which is the order the page's Run all windows uses (the page also runs at most four at once). A window that fails, times out or is rejected is reported in its line and does not stop the others, and the windows that referenced it still run. Windows with no SQL, and reference cycles with whatever waits on them, are skipped and named. All the snapshots are saved in **one** agent write, so one `undo_canvas` reverts them all; when nothing succeeded nothing is written (the last line is `nothing saved.`). It fails as a whole (an error result) when there is no connection or warehouse or no query window has SQL.
- **`chart` and `view`** (`add_query_window`, `add_nodes` with `type: query`, `update_nodes`). `chart` is a Vega-Lite v5 spec: an object with `mark` or `layer`, otherwise `chart must be a Vega-Lite spec`. It is stored as `{"vega_lite": spec}`. The page gives the chart the window's result as its data, with field names equal to the result's column names (give no `data`), so a chart is drawn once the window has a result, from `run_window` or from a run in the page. `view` is `results` or `chart`, the tab the window opens on; `view: chart` needs a chart on the window (an error otherwise). Both belong to query windows only. After a write, the report adds a note when a chart reads a field that the window's saved result does not have (it checks the encodings of the spec and its layers, and is silent when the spec has a `transform`). Tool descriptions carry two examples. A bar chart:

  ```json
  {"mark": "bar", "encoding": {"x": {"field": "category", "type": "nominal"}, "y": {"field": "rate", "type": "quantitative"}}}
  ```

  A range with a best estimate, from a one-row result with `low`, `high` and `best` columns, drawn as a bar from `x` to `x2` and a `rule` at the estimate (this is how to draw ranges and uncertainty, not from rectangles):

  ```json
  {"layer": [{"mark": "bar", "encoding": {"x": {"field": "low", "type": "quantitative"}, "x2": {"field": "high"}}},
             {"mark": "rule", "encoding": {"x": {"field": "best", "type": "quantitative"}}}]}
  ```

**The edit report.** Every canvas tool that changes a canvas saves it and returns:

```
added a, b. revision 4; doctor score 96/100 (1 warning). undo_canvas reverts it.
Canvas "d": 2 nodes (2 shape), 1 connectors; extent x 0..580, y 0..80 px. Layout score 96/100.
<the next lines of layout.describe, about 14 in all>
```

**Auto tidy.** After `add_nodes`, `add_query_window` and `update_nodes`, an overlap-only tidy (`layout.tidy` with `rules: ["overlaps"]`) runs on the nodes just touched, unless `auto_tidy: false`. The headline then says `moved N to clear overlaps`. Locked nodes never move.

**Undo.** Before each agent write, the file it replaces is kept as a snapshot in `data/canvas_history/<name>/` (the last 20 per canvas). A canvas that did not exist before has nothing to undo. `undo_canvas` and the page's "Undo agent change" button (`POST /api/canvases/<name>/undo`) restore the newest snapshot.

**Live sync.** Each canvas has a revision number (`GET /api/canvases/<name>/revision`, `contracts/api.md` section 3). Every save, by the page or by an agent, increments it. The page polls it every 2 seconds. With no unsaved edits it reloads the canvas in place and keeps its viewport. With unsaved edits it shows "An agent changed this canvas" with Reload and Keep mine, and its autosave waits for the choice. The page sends `X-Base-Revision` with a save, and the server answers `409` when the canvas moved on (`contracts/api.md`), so the page cannot overwrite an agent's save unseen. An agent write is never refused: MCP writes always go to the saved file.

## Tools: saved graphs

A saved graph is a diagram saved from the Graph tab: `data/diagrams/<name>.json` (`contracts/api.md`, "Diagrams"). It is a different store from a canvas, and `list_canvases` and `get_canvas` never see it (when a canvas name is missing but a graph has that name, `get_canvas` says to use `get_graph`; `list_canvases` with nothing to list points to `list_graphs`). The tools need no warehouse, write only local files, and the five that change a graph name **tables**, never edges or coordinates. A graph name is accepted as typed (`Returns graph`) or as stored (`Returns_graph`; other characters than letters, digits, `_`, `.` and `-` become `_`). Names that differ only by case are refused, as for canvases.

| Tool | Input | Output |
| --- | --- | --- |
| `list_graphs` | none | `name: N tables, M edges, revision R (by), saved <time>` per graph, plus `named 'Returns graph'` when the title differs from the stored name |
| `get_graph` | `*name`, `format` (`text` default, `json`) | Text: the header (counts, revision, who wrote last, saved time), the focus schema and what it is colored by, one line per table (`catalog.schema.table [kind] focus pinned`) and one per edge (`source -> target  kind (family) status (join columns)`, the family being `flow`, `reference` or `meaning`; `<->` for lineage both ways). The Graph's filters are not saved with a graph, so there are none to report. Then the groups (by schema unless the graph says otherwise: each with its table count and whether it is collapsed, by the default rule or by the person's choice) and the elided chains (`source -> target via N views: v1, v2`), worked out with the page's default filters. `json`: `{name, title, revision, by, saved_at, focus_schema, color_by, grouping: {by, chains}, groups: [{key, label, tables, count, collapsed, default_collapsed}], chains: [{id, source, target, views, edges}], nodes: [{table, kind, focus?, pinned?, x, y}], edges: [{id, kind, family, cardinality?, transform?, source, target, status, directed, bidir?, columns?, parent_columns?, note?}]}`, compact |
| `create_graph` | `*name`, `*tables` (1-60), `focus`, `color_by` | Saves a graph with a node for each table and an edge for each relationship the app knows between two of them. An existing name is an error. Needs a connected profile |
| `update_graph` | `*name`, `add`, `remove`, `relayout`, `color_by` | Adds or removes tables (their edges go with them), derives the edges again for the new set, keeps the positions of tables that stay unless `relayout`, and places added tables clear of them. With `graph` it also adds the traced tables to that saved graph as `update_graph` `add` does and says so (not read-only for that reason). `format: json` is the `GET /api/column-trace` body (`contracts/api.md` section 4). **Edges** are what the Graph tab draws for exactly those tables (no neighbors are added): the edges of `GET /api/relationships` (Unity Catalog foreign keys, view dependencies, lineage, and stored joins) with both ends in the set. Following the Graph's default filters, rejected edges are left out, and so are joins nobody has accepted yet (status `proposed`); manual and accepted ones are drawn. One edge per pair of tables, and edges marked `superseded` (lineage into a view whose definition no longer reads its source) are left out, as `relations()` decides, so the Graph tab and these tools share one rule. The result says how many superseded edges were left out, and names tables that have no relationship to the others. Every node is pinned (added on purpose), so the Graph's edge filters never hide it. The focus is `focus` (its schema becomes the focus schema), else none, with the most common schema as the focus schema.

**Layout** is left to right. Lineage and view dependencies set the columns (a source is left of what is built from it). A table that has only references (foreign keys, joins) or meaning links takes the column of the table it refers to or is referred by, one above the other. Parts of the graph with no edge between them are stacked in bands. It is deterministic.

**Live sync and revisions.** Each saved graph has a revision, kept in `data/diagram_history/<name>/meta.json` (it survives a delete, so a later graph of that name keeps counting). Every write bumps it: the page's Save, and an agent's `create_graph`, `update_graph` and `rename_graph` (`by` is `agent`). The Graph tab polls the open graph's revision every 2 seconds. With nothing changed on the page since it loaded or saved the graph, an agent's change is loaded in place; otherwise the page shows "<name> was changed by agent" with Reload and Keep mine. A Save over a newer revision asks "Overwrite newer save?" first (the page sends `X-Base-Revision`, `contracts/api.md`). An agent write is never refused. There is no undo for graphs; `delete_graph` leaves the copy in the trash folder.
